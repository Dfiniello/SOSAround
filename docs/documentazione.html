1. Cos'è SOSAround

SOSAround è una piattaforma per la gestione tempestiva degli smarrimenti (animali, oggetti). Chi perde qualcosa registra un Smart ID del bene e apre una segnalazione geolocalizzata; gli altri utenti vicini ricevono una notifica e possono contattare il proprietario per coordinare il ritrovamento, in tempo reale.

Funzionalità principali

  • Smart ID: registrazione di un bene (nome, tipo, foto, codice/microchip, QR).
  • Segnalazione: allerta geolocalizzata con raggio di prossimità.
  • Bacheca community + Mappa: elenco e mappa delle segnalazioni attive.
  • Chat 1:1 in tempo reale tra proprietario e ogni potenziale ritrovatore.
  • Notifiche realtime cross-device (nuove segnalazioni / nuovi messaggi).

3. La Clean Architecture lato client

Il client segue la Clean Architecture: il codice è diviso in cerchi concentrici dove le dipendenze puntano sempre verso l'interno. Il dominio non conosce React né la rete; l'infrastruttura implementa le interfacce del dominio.

Vantaggio pratico. Passare da Supabase al server proprio ha richiesto di cambiare solo l'infrastruttura (i repository e il realtime): dominio, use case e gran parte della UI sono rimasti invariati, perché dipendono dalle interfacce, non dall'implementazione.

5.3 Autenticazione — src/auth/jwt.ts

  • firmaToken({ idUtente }) → genera un JWT firmato (scadenza 30 giorni).
  • verificaToken(token) → verifica e restituisce il payload, o null.
  • authGuard → middleware Express: legge l'header Authorization: Bearer <token>, valida e popola req.idUtente; altrimenti risponde 401.

Le password non sono mai salvate in chiaro: bcrypt.hash in registrazione, bcrypt.compare al login.

5.4 Realtime — src/realtime/io.ts

Inizializza Socket.IO con autenticazione JWT all'handshake. I client entrano in stanze (room) per ricevere solo gli eventi pertinenti. Il server emette eventi dopo le scritture REST. 

// handshake autenticato col token JWT
io.use((socket, next) => {
  const payload = verificaToken(socket.handshake.auth?.token);
  if (!payload) return next(new Error('Non autorizzato'));
  socket.data.idUtente = payload.idUtente; next();
});

// stanze per la chat 1:1 (chiave = "idSegnalazione:idRitrovatore")
socket.on('join',  (key) => socket.join('chat:' + key));

// emit dopo l'INSERT in REST:
emitNuovaSegnalazione(row)              -> io.emit('segnalazione:nuova', row)
emitNuovoMessaggio(chiave, row)         -> io.to('chat:'+chiave).emit('messaggio:nuovo', row)
                                           io.emit('messaggio:nuovo:global', row)
Da Supabase a Socket.IO. Dove prima c'erano i postgres_changes di Supabase, ora è il nostro server a emettere esplicitamente gli eventi subito dopo aver salvato i dati.

6.3 Accesso ai dati — infrastructure/api e repositories/api

apiClient.ts è un piccolo wrapper su fetch: aggiunge l'header Authorization col JWT, serializza/deserializza JSON e ricava l'URL del server automaticamente dall'host con cui Expo serve l'app (così è sempre raggiungibile dal telefono).

I Api*Repository implementano le interfacce del dominio convertendo tra le righe del database (snake_case) e le entità (camelCase). Esempio (ApiSegnalazioneRepository):

  return rows.map(rowToSegnalazione);   // Row(snake_case) -> Segnalazione(camelCase)

7. Comunicazione client ↔ server

Due canali complementari:

  • REST per leggere/scrivere dati (richiesta→risposta). Autenticato col JWT in header.
  • WebSocket per il tempo reale (il server "spinge" gli eventi ai client). Autenticato col JWT all'handshake.

Esempio combinato: il client salva un messaggio via POST /messaggi (REST); il server, dopo l'INSERT, emette messaggio:nuovo nella stanza della conversazione (WebSocket), e l'altro partecipante lo riceve all'istante senza ricaricare.

8. I flussi principali passo-passo

8.1 Registrazione / Login

  1. L'utente compila AuthScreen; AuthService.validaEmail/validaPassword controllano i campi.
  2. AuthService.login() chiama POST /auth/login; il server verifica con bcrypt e ritorna { token, utente }.
  3. Il token viene salvato in SecureStore (storage cifrato) e tenuto in memoria per gli header.
  4. Dispatch loginSuccess(utente) → la UI passa alle tab principali; connettiSocket() apre il canale realtime.

8.2 Creazione di una segnalazione

  1. NuovaSegnalazioneScreen: l'utente sceglie il punto sulla mappa e descrive il bene.
  2. AllertaController.attivaAllerta() esegue AttivaAllertaUseCase: crea lo Smart ID e salva la Segnalazione via POST /segnalazioni.
  3. Il server salva su SQLite ed emette segnalazione:nuova a tutti i client.
  4. Sul device del creatore la segnalazione viene aggiunta allo store in modo idempotente (niente doppioni con l'evento realtime).
  5. Gli altri utenti ricevono l'evento: la Bacheca si aggiorna e parte una notifica locale.

8.3 Chat 1:1 proprietario ↔ ritrovatore

  1. Un ritrovatore preme "Contatta" in Bacheca → naviga a ChatScreen con { idSegnalazione, idProprietario, idRitrovatore = me }.
  2. ChatScreen calcola la chiave idSegnalazione:idRitrovatore, carica i messaggi (GET /messaggi?…&ritrovatore=…) ed entra nella stanza chat:<chiave>.
  3. All'invio, ComunicazioneRealtimeUseCase calcola il destinatario: se scrive il proprietario → destinatario è il ritrovatore; altrimenti → il proprietario.
  4. Il server salva il messaggio ed emette messaggio:nuovo solo nella stanza della coppia: nessun altro utente della community lo vede.
  5. Il proprietario vede tutte le sue conversazioni (una per ritrovatore) nella tab Messaggi.
Isolamento garantito. Poiché la stanza include il ritrovatore, due ritrovatori diversi che contattano lo stesso proprietario hanno conversazioni completamente separate.
